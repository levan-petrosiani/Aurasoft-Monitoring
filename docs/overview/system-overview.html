1. Summary

The API Test Tool (aqt) checks whether a bank's open-banking API (XS2A, Berlin Group NextGenPSD2 as profiled for Georgia) behaves the way the standard requires. It acts like a real third-party app (TPP): mutual TLS with a QWAC certificate, every request signed with a QSealC (Digest + X-Jws-Signature), OAuth2 with PKCE for customer authentication, and every response checked against the standard. Tests are YAML scenarios; banks are YAML profiles; a built-in MockBank lets everything run without a real bank. It now covers both halves of open banking: account information (AIS) and payment initiation (PIS).

The AI layer on top of it is built so that every AI output is traceable and checked:

  • Store everything (Phase 0): runs, scenarios, steps, HTTP exchanges and events in PostgreSQL, masked before writing; every model call audited.
  • AI run summaries (Phase 1): a triage of each run — causes, who is at fault, evidence, clause, next step, what changed.
  • Rules from the standards (Phase 2): the AI drafts rules from a clause with the exact sentence they rest on; code verifies every quote; a person approves.
  • Test scenarios from approved rules (Phase 3): the AI writes a scenario; code loads it, runs it on MockBank, feeds errors back; a person approves; a coverage view links clause → rule → scenario → result per bank.
  • Ask agent (Phase 4): staff ask questions in plain language; the agent answers with read-only tools and its citations are checked in code.
  • Payment initiation (Phase 5): MockBank payments and a pis suite, gated to sandbox test accounts.
  • Monitoring (Phase 6): scheduled runs, regression alerts (+ webhook), trends, retention.
  • Eval sets: fixed cases with known answers for every AI feature, scored in code — and a measured comparison of Claude with the local model (chapter 13).
Design principle. Facts are computed in code; judgement comes from the model; a person approves. Counts, run-to-run changes, ids, quotes, dry-run results and alerts are computed or checked in code. The model groups, explains and drafts. Nothing the AI drafts becomes a rule or a test until a human approves it, the test engine contains no AI, and the AI is graded by code, never by another model.

2. The problem and the approach

The problem

  • Writing conformance tests by hand from a 341-page standard (plus Georgian profiles) is slow, and it is hard to say which requirements are covered.
  • Test results are long and technical; working out why a run failed, and whether it is the bank or our side, takes an expert.
  • History lives in report folders; nobody can ask "when did this bank start failing?", and nobody notices when it does.

The approach — and why it is shaped this way

Original ideaWhat we built, and why
AI writes tests directly from the documentsDocument → approved rule → test. A one-line rule with its quote can be reviewed in seconds; every generated test traces back to a sentence of the standard and is proven on MockBank before a person sees it.
AI "tests the APIs"The AI writes, the engine runs. The model never calls a bank; results stay reproducible.
AI summariesTriage, not prose: grouped by cause, bank vs our side, evidence, clause, next step; facts computed in code.
Rule drafting with human approvalKept and strengthened: quotes are verified in code; a failed quote goes back to the model once.
Store every data / monitoringKept, with masking before writing, an audit log, and alerts computed in code after every run.
RAG agent over logsAn agent with query tools (counts and time ranges need SQL, not similarity search); its SQL runs under a read-only database login.

Model choice: measured, not assumed

Every feature defaults to Claude (claude-opus-5-5, now verified live). A local model (qwen3:8b via Ollama) stays available as an opt-in for offline use or when no data may leave the machine. The eval sets measured both on the same 18 cases: Claude passed 18/18 (100% of checks), the local model 14/18 (93%), and Claude was about 4× faster in total. Embeddings for search are always local (bge-m3).

4. How a test run works

A run takes a bank profile and a set of scenarios. Preflight scenarios (certificates, TLS, OAuth discovery, a signed request) always run first; if a critical one fails, the rest are marked Blocked instead of failing one by one for the same reason. Each scenario is a list of steps; each request is signed, sent over mutual TLS, and its response is checked (status, error codes, headers, JSON fields, signature). 

sequenceDiagram
  autonumber
  participant R as Runner (our tool, acting as TPP)
  participant B as Bank XS2A API
  participant A as Bank auth server
  participant U as Tester (browser)
  participant S as Store
  R->>B: POST consent (mTLS, Digest, X-Jws-Signature)
  B-->>R: 201 consentId + link to start authorisation
  R->>B: POST start authorisation
  B-->>R: 201 link to OAuth
  R->>U: open login page (PKCE, state)
  U->>A: log in and approve
  A-->>R: redirect with code
  R->>A: exchange code for token (mTLS)
  R->>B: read accounts and balances (consent + token)
  R->>B: delete consent (cleanup)
  R->>S: results + masked exchanges + events
Figure 2 — An account-information scenario (AIS-001) from start to store.
OutcomeMeaning
PassedAll expectations met.
FailedThe bank's API did not behave as expected (a bank-side deviation).
ErrorA problem on our side: configuration, certificates, timeout waiting for a login.
BlockedNot run because a critical preflight check failed.
SkippedThe bank does not declare the feature (expected; not a problem).

Requests can poll (repeat until a status is final, e.g. a payment settling) and expectations can accept one of several values. Unattended runs (monitoring) skip scenarios that need a person to log in, unless the login is automatic (MockBank).

Reports are written as before (report.html, summary.json, junit.xml), and the run is also saved to the database. A database problem never fails a run: it becomes a notice, and the folder can be imported later.

The Ask agent's SQL cannot escape. It logs in as its own database role aqt_agent, which can only read the agent views: one prepared statement, read-only, 5-second timeout. A first design switched role inside the main connection; probing showed the SQL could switch back (set_config('role', …), a second statement), so it was replaced. The database now refuses every escape attempt, and a test proves it.

Audit

Every model call — summaries, drafting, the Ask agent's tool rounds, eval runs — is a row in ai_calls (feature, provider, model, who, masked request, answer, tokens, duration, prompt hash). Rule decisions are rows in rule_reviews, scenario approvals link the rule, alerts record who acknowledged them.

Safeguards in the provider layer

  • Refusal fallback: our prompts contain security-testing material; a declined request is re-run on Anthropic's recommended fallback model.
  • Tool calling: Claude's own blocks (including thinking) are sent back unchanged in a tool loop, as the API requires; tested against a fake server.
  • Context window and timeouts for the local model; timeouts are audited failures.
  • Prompts and their JSON schemas are files in aqt/ai/prompts/, reviewed like code and measured with aqt ai eval before and after a change.
Claude verified live (25 October): aqt ai check answers in about 2 s through the beta endpoint with the refusal fallback, and the full eval set ran against it (35 calls, 130,607 input / 23,715 output tokens). The key comes from a git-ignored .env; values are never printed.

A summary contains: a health verdict (healthy / degraded / broken / inconclusive), findings grouped by root cause, each with the side at fault (bank, our side, environment, unclear), evidence quoted from the responses, the clause, and a next step; the change since the previous run; and warnings worth a look.

Evaluation on real data

All 9 stored runs with results were summarized with the local model and compared with the database. Five kinds of error were found and each was fixed — preferably in code:

Error foundFix
"Since the previous run" described changes wronglyNow written in code from the computed changes
Warnings of passed scenarios reported as problemsCode moves them to "worth a look"; findings about skipped scenarios are dropped (Python port)
Random 503s of the TBC test sandbox blamed on the bankPrompt: temporary 5xx = environment unless persistent
A tester clicking "Deny" treated as a critical bank faultPrompt: access_denied at login = unclear, suggest a re-run
A correct but shortened clause reference was removedValidator matches clause numbers and restores the run's exact wording
Our expired certificate blamed on the bank (found by the eval set)Code marks local certificate checks as ours in the digest; prompt: certificate/signature problems are our side
After the fixes, re-run on the 5 affected runs: all correct against the data. The real TBC deviation (global consent rejected with FORMAT_ERROR instead of PARAMETER_NOT_SUPPORTED) is found every time with the right clause. Local speed: 15–35 s per run.

  • PDF: the table of contents gives the clause list; each entry is found in order in the body; deeper sections (e.g. 6.3.1.2) are found inside their parent. Running headers and footers are dropped by pattern (pdfplumber puts footers last). A defect in the PDF (a stray sentence glued into the chapter 6 heading) is corrected in the manifest. The Python reader gives the same 182 clauses as the C# one; every existing rule quote still verifies.
  • Word: heading styles give the structure; numbers are computed like Word. Verified against the published PDF of the Georgian guide, because the document's own cross-references contradict each other.
  • The Georgian guides exist only in Georgian. The Georgian text is the source of truth; each rule carries an English translation of its quote, labelled as an AI translation.
  • Documents are downloaded, not committed; a changed file (different SHA-256) is refused until reviewed.

Checks done in code before a person sees a draft

CheckEffect
Quote occurs in the clauseIgnores only spacing, line breaks, hyphenation, quote/dash style and case; "…" marks skipped words. Fails → rule stored as invalid (kept, never reviewable).
Repair roundQuotes that fail the check go back to the model once with the verifier's reason ("copy exactly or remove"); the new answer is checked again. Added after the eval set showed the local model rebuilding table rows ("Code 202: …") that the standard does not contain.
Level vs wordingMUST/SHOULD/MAY must be backed by the quote's keywords (English and Georgian); otherwise a warning for the reviewer.
DuplicatesClose in meaning (embeddings) and naming the same fields, codes and statuses; otherwise "accept availableAccounts" and "accept allPsd2" looked identical.
ReviewApprove only drafts; reject needs a reason; an edited quote is checked again; a stale update is refused; every action recorded with the reviewer's name.
Findings from the first drafts (local model). It finds requirements and quotes them exactly, including Georgian — it found the Georgia-specific 90-day consent limit (PERIOD_INVALID), which the Berlin Group guide does not have. Its weak point is the level: it marks optional functions as MUST; the level check flags this to the reviewer. In clause 4.1 it joined non-adjacent bullet items without "…": the quote check correctly rejected 8 such drafts (the prompt now forbids it). On GE-XS2A 9.2.2 it changed one Georgian word inside a quote (სათაურის → სათავის), and the check caught that too.

When a draft fails on MockBank, the model may answer that the scenario is right and MockBank does not implement the rule. That claim is accepted only when an expectation failed (never for a tool error) and is shown to the reviewer. The first live draft did exactly this: GE-CON-001 (90-day consent limit) failed because MockBank had no such limit — so the limit was added to MockBank, and the same draft then passed on the first attempt.

The Coverage page and aqt coverage show, per approved rule: its clause, the scenarios that verify it, and their last result on each bank — computed in code from the rules, the rules: field of the scenario files and the stored runs. aqt validate warns when a scenario cites a rule that is missing or not approved.

A payment moves money, so it is gated twice. PIS scenarios run only when a bank profile names its sandbox test accounts (variables.pis) — the TBC mock has none and skips the whole suite. AI-drafted scenarios that send payment data without that requirement are refused in code; a live draft that slipped past the first version of this check (payment data sent to a signing-basket path) led to the check being widened and tested.

Also found: MockBank's sandbox IBANs had invalid check digits — a real bank would have rejected them. Not built: bulk and periodic payments, signing baskets.

Decision. Claude is the default for every feature: it passed 18 of 18 cases (100% of checks) and was about 4× faster. 18. Key decisions

DecisionChoice and reason
LanguagePython (team decision; the teammates ported the engine, verified both ways against the C# client and MockBank). The AI layer was ported to match.
DatabasePostgreSQL (Docker) with pgvector: one database for runs, audit, clauses and vectors. Python uses plain SQL on the same schema; the database the C# tool created is kept.
ModelsClaude by default for every feature (measured: chapter 13); local Ollama model opt-in only; local embeddings.
Local modelqwen3:8b when chosen (5× faster than gemma4:26b); kept for offline / no-data-leaving use.
Scenario draftsCode owns ids and links to the standard; MockBank-only dry runs; approval writes the file.
Ask agentRead-only tools; SQL under its own database login; citations checked in code.
PaymentsGated to sandbox test accounts named in the profile; enforced in code for AI drafts.
MonitoringSchedules in YAML (versioned); alerts in code; unattended runs never wait for a login.
AI qualityEval sets graded in code, never by a model; run before and after every prompt change.
StandardsLatest versions: Berlin Group IG 1.3.16; Georgian guides from openfinance.ge (Georgian only).
TranslationNo whole-document translation; Georgian text is the source of truth; per-rule English translation labelled as AI.
Rules storageDatabase is the source of truth (queue, history, search); approved rules exported to YAML for git.
ApprovalThe team approves now; real staff later (needs login). Every action recorded with name, time and reason.
ScopeAIS first; PIS designed in from the start, built in Phase 5.
RepositoryPublic GitHub repository; source documents not committed (licences); no secrets committed.

python -m venv .venv && source .venv/bin/activate
pip install -e ".[test,ai]"
docker compose up -d                                   # PostgreSQL + pgvector on localhost:5435
aqt db migrate
aqt db import reports

# a full test run against the built-in fake bank, saved to the database
aqt run --bank MOCK --with-mock --sca-auto --db "Host=localhost;Port=5435;Database=aqt;Username=aqt;Password=aqt_dev"

# AI: put ANTHROPIC_API_KEY=... in .env (git-ignored); Ollama with bge-m3 for search (qwen3:8b optional)
aqt ai check
aqt ai summarize latest
aqt ai eval --provider anthropic                       # eval sets; reports in reports/evals/

# standards and rules
aqt standards fetch && aqt standards ingest
aqt rules draft GE-XS2A:0.8.RC3:9.1.1.10
aqt scenarios draft GE-CON-001                         # needs an approved rule; dry run on MockBank
aqt coverage
aqt ask "Why did TBC fail on 21 October?"
aqt monitor status                                     # schedules in monitoring.yaml

# web portal (store/AI pages on when the database is reachable)
aqt portal                                             # http://localhost:5280

# tests (including database tests)
AQT_TEST_DB="host=localhost port=5435 user=aqt password=aqt_dev" pytest
