1. Summary

The API Test Tool (aqt) checks whether a bank's open-banking API (XS2A, Berlin Group NextGenPSD2 as profiled for Georgia) behaves the way the standard requires. It acts like a real third-party app (TPP): mutual TLS with a QWAC certificate, every request signed with a QSealC (Digest + X-Jws-Signature), OAuth2 with PKCE for customer authentication, and every response checked against the standard. Tests are YAML scenarios; banks are YAML profiles; a built-in MockBank lets everything run without a real bank. The tool was first built in C#/.NET; the team then moved it to Python, and the AI layer described here was ported with it (same database, prompts and checks).

This project adds an AI layer on top of that tool, built so that every AI output is traceable and checked:

  • Store everything (Phase 0): every run, scenario, step, HTTP exchange and event goes to PostgreSQL, with tokens, authorization codes and IBANs masked before writing. Every model call is audited.
  • AI run summaries (Phase 1): one click turns a run into a triage: problems grouped by cause, who is at fault (bank, our side, environment), evidence, clause, next step, and what changed since the bank's previous run.
  • Rules from the standards (Phase 2): the Berlin Group guide and the Georgian guides are split into clauses and made searchable (also across English ↔ Georgian). The AI drafts rules from a clause, each with the exact sentence it rests on; code verifies every quote; a person approves each rule before it counts.
Design principle. Facts are computed in code; judgement comes from the model; a person approves. Counts, run-to-run changes, scenario ids and clause references are computed or checked in code. The model groups, explains and drafts. Nothing the AI drafts becomes a rule or a test until a human approves it, and the test engine itself contains no AI: results stay reproducible.

2. The problem and the approach

The problem

  • Writing conformance tests by hand from a 341-page standard (plus Georgian profiles) is slow, and it is hard to say which requirements are covered and which are not.
  • Test results are long and technical; working out why a run failed, and whether it is the bank or our side, takes an expert.
  • History lives in report folders; nobody can ask "when did this bank start failing?".

The approach — and why it is shaped this way

Original ideaWhat we built instead, and why
AI writes tests directly from the documentsDocument → approved rule → test. A one-line rule with its quote can be reviewed in seconds; a generated test file cannot. Every future test traces back to a sentence of the standard.
AI "tests the APIs"The AI writes, the engine runs. The model never calls a bank. Results are reproducible from YAML and auditable.
AI summariesTriage, not prose: grouped by cause, bank vs our side, evidence, clause, next step; facts computed in code.
Rule drafting with human approvalKept, and strengthened: the quote is verified in code, so a rule can never rest on words the standard does not contain.
Store every dataKept, with masking before writing (tokens, codes, PSU ids, IBANs) and an audit log of every AI call.
RAG agent over logsAn agent with query tools over the database for logs (counts and time ranges need SQL, not similarity search); retrieval only for the standards text. (Phase 4)

Model choice: cloud and local

Drafting reads only public standards, so it uses Claude (best accuracy; claude-opus-5-5). Features that see run data (summaries, the future ask-agent) can be switched to a local model via Ollama so data never leaves the machine. Embeddings for search are always local (bge-m3). The default local chat model is qwen3:8b (5 GB): it summarized a run in 35 s versus 190 s for gemma4:26b (17 GB) with the same root cause found.

4. How a test run works

A run takes a bank profile and a set of scenarios. Preflight scenarios (certificates, TLS, OAuth discovery, a signed request) always run first; if a critical one fails, the rest are marked Blocked instead of failing one by one for the same reason. Each scenario is a list of steps; each request is signed, sent over mutual TLS, and its response is checked (status, error codes, headers, JSON fields, signature).

  participant B as Bank XS2A API
  participant A as Bank auth server
  participant U as Tester (browser)
  participant S as Store
  R->>B: POST consent (mTLS, Digest, X-Jws-Signature)
  B-->>R: 201 consentId + link to start authorisation
  R->>B: POST start authorisation
  B-->>R: 201 link to OAuth
  R->>U: open login page (PKCE, state)
  U->>A: log in and approve
  A-->>R: redirect with code
  R->>A: exchange code for token (mTLS)
  R->>B: read accounts and balances (consent + token)
  R->>B: delete consent (cleanup)
  R->>S: results + masked exchanges + events
Figure 2 — An account-information scenario (AIS-001) from start to store.
OutcomeMeaning
PassedAll expectations met.
FailedThe bank's API did not behave as expected (a bank-side deviation).
ErrorA problem on our side: configuration, certificates, timeout waiting for a login.
BlockedNot run because a critical preflight check failed.
SkippedThe bank does not declare the feature (expected; not a problem).

Reports are written as before (report.html, summary.json, junit.xml), and the run is also saved to the database. A database problem never fails a run: it becomes a notice, and the folder can be imported later.

Safeguards in the provider layer

  • Refusal fallback: our prompts contain security-testing material (signatures, tokens, auth flows) that can trip a model's safety filters; a declined request is re-run on Anthropic's recommended fallback model instead of failing.
  • Context window: Ollama silently cuts prompts longer than its default window; every local call now sets 16k tokens.
  • Timeouts are recorded as failures (not as user cancellation), so they appear in the audit log.
  • The exact request sent to Claude is checked by a test against a local fake Anthropic server (model, limits, effort, fallback header, streaming) — no key needed.
  • Prompts and their JSON schemas are files in aqt/ai/prompts/, reviewed like code.
Not yet verified live: calls to Claude. No ANTHROPIC_API_KEY has been set, so all live AI results so far come from the local qwen3:8b. The Claude request format is verified offline.

A summary contains: a health verdict (healthy / degraded / broken / inconclusive), findings grouped by root cause, each with the side at fault (bank, our side, environment, unclear), evidence quoted from the responses, the clause, and a next step; the change since the previous run; and warnings worth a look.

Evaluation on real data

All 9 stored runs with results were summarized with the local model and compared with the database. Five kinds of error were found and each was fixed — preferably in code:

Error foundFix
"Since the previous run" described changes wronglyNow written in code from the computed changes
Warnings of passed scenarios reported as problemsCode moves them to "worth a look"; findings about skipped scenarios are dropped (Python port)
Random 503s of the TBC test sandbox blamed on the bankPrompt: temporary 5xx = environment unless persistent
A tester clicking "Deny" treated as a critical bank faultPrompt: access_denied at login = unclear, suggest a re-run
A correct but shortened clause reference was removedValidator matches clause numbers and restores the run's exact wording
After the fixes, re-run on the 5 affected runs: all correct against the data. The real TBC deviation (global consent rejected with FORMAT_ERROR instead of PARAMETER_NOT_SUPPORTED) is found every time with the right clause. Local speed: 15–35 s per run.

The standards

  • PDF: the table of contents gives the clause list; each entry is found in order in the body; deeper sections (e.g. 6.3.1.2) are found inside their parent. Running headers and footers are dropped by pattern (pdfplumber puts footers last). A defect in the PDF (a stray sentence glued into the chapter 6 heading) is corrected in the manifest. The Python reader gives the same 182 clauses as the C# one; every existing rule quote still verifies.
  • Word: heading styles give the structure; numbers are computed like Word. Verified against the published PDF of the Georgian guide, because the document's own cross-references contradict each other.
  • The Georgian guides exist only in Georgian. The Georgian text is the source of truth; each rule carries an English translation of its quote, labelled as an AI translation.
  • Documents are downloaded, not committed; a changed file (different SHA-256) is refused until reviewed.

Checks done in code before a person sees a draft

CheckEffect
Quote occurs in the clauseIgnores only spacing, line breaks, hyphenation, quote/dash style and case; "…" marks skipped words. Fails → rule stored as invalid (kept, never reviewable).
Level vs wordingMUST/SHOULD/MAY must be backed by the quote's keywords (English and Georgian); otherwise a warning for the reviewer.
DuplicatesClose in meaning (embeddings) and naming the same fields, codes and statuses; otherwise "accept availableAccounts" and "accept allPsd2" looked identical.
ReviewApprove only drafts; reject needs a reason; an edited quote is checked again; a stale update is refused; every action recorded with the reviewer's name.
Findings from the first drafts (local model). It finds requirements and quotes them exactly, including Georgian — it found the Georgia-specific 90-day consent limit (PERIOD_INVALID), which the Berlin Group guide does not have. Its weak point is the level: it marks optional functions as MUST; the level check flags this to the reviewer. In clause 4.1 it joined non-adjacent bullet items without "…": the quote check correctly rejected 8 such drafts (the prompt now forbids it). On GE-XS2A 9.2.2 it changed one Georgian word inside a quote (სათაურის → სათავის), and the check caught that too.

TranslationNo whole-document translation; Georgian text is the source of truth; per-rule English translation labelled as AI.

ApprovalThe team approves now; real staff later (needs login). Every action recorded with name, time and reason.
ScopeAIS first; PIS designed in from the start, built in Phase 5.
Logs Q&AAgent with database tools, not vector search over logs.
RepositoryPublic GitHub repository; source documents not committed (licences); no secrets committed.
